# sgit axioms

## AX-SGIT-BRANCH-UPSTREAM-SELF: A Branch Cut By sgit-core Carries No Inherited Upstream, And Every sgit-core Push Names Its Destination Explicitly

A branch newly cut by sgit-core MUST NOT inherit the start-point base as its
upstream. Every sgit-core push MUST name its destination with an explicit
`HEAD:refs/heads/<branch>` refspec.

- In the new-branch arm of `git worktree add`, pass `--no-track` when the start
  point is `origin/<base>` (or HEAD). Leave the `--track` arm alone: a branch
  whose remote counterpart already exists MUST track itself
  (`branch.<name>.merge == refs/heads/<name>`).
- Push with `git push --set-upstream origin HEAD:refs/heads/<branch>`. Keep
  `--set-upstream` so branches created before this rule self-repair on their
  next push. Never reintroduce a source-only `push --set-upstream origin
  <branch>` refspec in sgit-core.

### Why

Cutting a branch from a remote-tracking start point makes git's default
`branch.autoSetupMerge=true` set the new branch's upstream to the BASE it was
cut from (`merge = refs/heads/main`). Combined with `push.default = upstream`
— set on real machines — a destination-less `push --set-upstream origin
<branch>` then resolves its destination to the base and writes feature commits
onto main, silently bypassing the PR and lander pipeline. sgit-core owns both
halves of this hazard (it creates branches at checkout.rs and pushes them at
shove.rs) and is stokd's only production push-with-sync path, so this is the
only place the invariant can be enforced for both the sgit and stokd binaries.
The rule was previously carried only by prose comments citing a nonexistent
`AX-CLI-BRANCH-UPSTREAM-SELF`, which is precisely how one patched copy and four
unpatched forks coexisted.

### How to apply

- In sgit-core's new-branch arm pass `--no-track`; leave the `--track` arm
  alone, because a branch whose remote counterpart already exists must track
  itself.
- Push with an explicit `HEAD:refs/heads/<branch>` refspec, retaining
  `--set-upstream` so branches created before this fix self-repair on their
  next push.
- Never reintroduce a `worktree add ... -b` without `--no-track` or a
  source-only `push` refspec in sgit-core.
- Route stokd's worktree creators through this primitive rather than forking
  it; a fork is what defeated the previous fix.

### Acceptance Checks

- `bash tests/validation/sgit-branch-upstream-self.test.sh`
- `cd apps/sgit && cargo test -p sgit-core --lib -- --test-threads=1`

### Enforcement
computational

## AX-CLI-CHECKOUT-REPO-TARGET: `sgit checkout <owner/repo|reponame>` Ensures A Valid Linked Main Worktree

`sgit checkout` MUST accept repository targets in addition to branch names:

- Outside a git repository, every target is a **repo target**.
- Inside a git repository:
  - local or `origin/<name>` branch → **branch target**
  - slash form under a branch namespace (`feature/`, `task/`, `project/`,
    `fix/`, …) → **branch target** (never misread as owner/repo)
  - GitHub-shaped `owner/repo` (or a path already present under bare/worktree
    roots) → **repo target**; if ensure fails, fall back to branch create
  - bare `reponame` with no matching branch → **repo target** via the same
    owner-resolution chain as `sgit clone` / `sgit open`, with branch-create
    fallback on failure

For a repo target, `sgit checkout` MUST:

1. Create all missing ancestors of the bare and main-worktree paths under the
   configured `bareRoot` / worktree root (never fail with a "can't write /
   No such file" error solely because those parents are missing).
2. Bare-clone when the bare is missing; materialize the main worktree when
   missing.
3. When the main worktree path exists but is **not** a valid linked worktree of
   the bare (missing or broken `.git`, or `git rev-parse` fails), re-materialize
   when safe (empty directory, or only a broken `.git` marker). Refuse with a
   clear error when non-git content would be destroyed.
4. After success, `git -C <path> rev-parse --is-inside-work-tree` is true and the
   common git dir is the bare. Print the absolute path on stdout only.

Complements [[ax-cli-checkout-sibling-worktree]] (branch path) without changing
the sibling-worktree / never-switch-in-place invariant.

### Why

Users navigate with `sgit checkout owner/repo` expecting ensure + `cd`. Treating
that form as a branch of the *current* repo creates wrong trees; missing parent
directories fail with write errors; existing non-git directories can be reported
ready without a git connection. A single verb that ensures a valid linked main
worktree keeps repo navigation aligned with the bare + worktree layout.

### How to apply

- Classify in `sgit-core` (`classify_checkout_target`); implement ensure in
  `ensure_repo_main_worktree` / `ensure_repo_main_worktree_from_url`.
- Reuse `bare_clone_from_url` + `create_worktree`; validate with
  `is_valid_linked_worktree` after every create.
- When `extensions.worktreeConfig` is enabled on the bare, write
  `core.bare=false` on the new worktree (same fix as submodule attach).
- CLI prints only the absolute path on stdout; diagnostics on stderr.
- Do not treat non-git directories as already-healthy worktrees in clone/open/checkout.

### Acceptance Checks

- `cargo test -p sgit-core checkout`
- `cargo test -p sgit checkout_parses_branch_arg`

## AX-SGIT-SHOVE-DETERMINISTIC-RECOVERY: `sgit shove` Always Terminates Pushed Or Cleanly Restored

`sgit shove` (and therefore `stokd shove`, which runs the same `sgit-core` flow)
MUST terminate in exactly one of two observable states:

- **(a) pushed** — the branch is on origin; or
- **(b) nothing pushed and restored** — the worktree is clean and NOT
  mid-operation, and the error names both safety backup branches.

It MUST NOT leave a rebase, merge, or cherry-pick in progress on any failure
path. Specifically:

1. **Stale-lock reaping is mechanical, never modelled.** Before mutating
   anything, shove MUST reap stale git lock files (`index.lock`, `HEAD.lock`,
   `shallow.lock` under the worktree's git dir) **only** when no live process
   holds them, and MUST fail fast naming the holding PID when one does.
2. **Shove serializes against itself.** Shove MUST hold a repo-scoped sgit lock
   so two concurrent shoves in one worktree cannot race each other's index.
3. **Pre-existing in-progress state is explicit.** Shove MUST detect
   `rebase-merge/`, `rebase-apply/`, `MERGE_HEAD`, or `CHERRY_PICK_HEAD` on
   entry and either adopt or abort it explicitly — never proceed over it.
4. **Sync failure is classified, not boolean.** A failed `git pull --rebase`
   MUST be classified as `Completed | Conflicts | Blocked | Fatal`. Only
   `Conflicts` may dispatch a `ConflictResolver`; `Blocked` gets bounded
   remediation plus retry; `Fatal` aborts and restores. An empty unmerged-path
   set MUST NEVER be reported as a successful resolution.
5. **Conflict resolution loops.** Resolution MUST loop until no rebase is in
   progress, because a rebase stops once per conflicting commit.
6. **Binary conflicts are their own class.** Conflicts on binary paths MUST be
   surfaced to the resolver as a distinct class carrying an ours/theirs/newest
   decision, and MUST NEVER be marker-scanned.

Complements the `ConflictResolver` seam without changing it: mechanical recovery
belongs below the seam so `sgit` (editor resolver) and `stokd` (agent resolver)
inherit it identically.

### Why

`push_with_sync` treats any `pull --rebase` failure as a conflict
(`crates/sgit-core/src/shove.rs:192`) and any empty unmerged set as a successful
resolution (`crates/sgit-core/src/shove.rs:252-256`). A stale `index.lock` left
by a killed sibling process therefore produced a silent no-op "resolution", a
guaranteed non-fast-forward push rejection, and a worktree stranded mid-rebase
whose retry then fails differently — the observed `stokd-cloud/mono` failure.
Recoverability must be mechanical and deterministic; model escalation is for
semantic conflicts only, never for environment faults.

### How to apply

- Keep every recovery step in `sgit-core` **below** the `ConflictResolver` seam.
- Add lock reaping and in-progress-state detection as pure, unit-testable
  classifiers in `shove.rs` (path/mtime/holder inputs in, decision out).
- Serialize with `sgit-core/src/lock.rs` rather than a second locking scheme.
- Replace the boolean branch in `push_with_sync` with a `SyncOutcome` enum;
  never collapse `Blocked` into `Conflicts`.
- Escalate to a resolver only for text and structural conflicts already
  classified by `UnmergedKind`; binary paths carry an explicit side choice.

### Acceptance Checks

- `cargo test -p sgit-core shove`
- `cargo test -p sgit-core lock`
- `cargo test -p sgit shove`

## AX-CORE-CONFIG-DISCOVERY-ORDER: Config Discovery Is `SGIT_CONFIG` → `~/.stokd` → `~/.sgit` → XDG

sgit resolves its repositories/git config from exactly these sources, in this
order, first hit wins:

1. `SGIT_CONFIG` — explicit path override. Wins unconditionally when set and
   non-empty (whitespace-only is ignored); a missing file is a load **error**,
   never a silent fall-through.
2. `~/.stokd/config.yaml` — continuity, when the file exists.
3. `~/.sgit/config.yaml` — sgit's own default config home, when the file exists.
4. `$XDG_CONFIG_HOME/sgit/config.yaml` (default `~/.config/sgit/config.yaml`),
   when the file exists.
5. Compiled defaults ([`RepositoriesConfig::default`]).

Sources 2–4 are skipped unless the file exists.

### Why

sgit must keep working unchanged on machines already configured by stokd, while
owning a first-class default home of its own for standalone installs. XDG stays
supported but ranks last so an accidental or stale `~/.config/sgit/config.yaml`
can never silently override the operator's real config. Precedence is durable,
cross-cutting behavior that every path, worktree, and land resolution depends
on, so it is pinned here rather than left implicit in one function's ordering.

### How to apply

- Define the order in exactly one place: `sgit_core::config::resolve_config_path_from`,
  which is pure and injectable (`sgit_config_env`, `home`, `xdg_config_home`) so
  precedence is unit-testable without mutating process env.
- `resolve_config_path()` is a thin wrapper that reads `SGIT_CONFIG`,
  `dirs::home_dir()`, and `XDG_CONFIG_HOME`, then delegates.
- Every source reports a distinct `ConfigSource` variant (`SgitConfigEnv`,
  `StokdContinuity`, `SgitHome`, `Xdg`, `Defaults`) so diagnostics can name the
  file actually in use.
- Do not add a new config location or reorder these without amending this axiom.

### Acceptance Checks

- `cargo test -p sgit-core config`

## AX-SGIT-PIN-REFUSAL-IS-ATOMIC: A Refused Branch Switch Leaves The Worktree Byte-Identical, Not Merely HEAD Unmoved

When the worktree branch pin refuses a switch, the worktree MUST end up exactly
as it was before the attempt — same index, same working-tree files — not merely
with an unmoved `HEAD`. The `prepared`-phase refusal writes a
`<marker>.refused` sentinel into the worktree gitdir, and the `aborted` phase
(which git invokes after a hook rejection) consumes that sentinel and restores
the tree with `git read-tree -m -u HEAD`. The repair is sentinel-gated so an
aborted ref transaction the pin never refused can never touch the working tree,
and it MUST NEVER use `git reset --hard` or `git clean` — a refused switch must
not be able to destroy uncommitted work. If the restore fails, the hook prints
the exact recovery command rather than failing the transaction differently.

### Why

Git rewrites the index and working tree BEFORE it opens the `HEAD` ref
transaction, so blocking at `prepared` stopped the ref move while leaving the
*other* branch's files checked out under an unmoved `HEAD`. The pinned worktree
was left with the wrong tree (observed: 3969 staged changes in the mono's `main`
worktree after one refused switch), which reads to every tool and human as "main
turned into another branch" — and the repo's `git add -A` auto-commit paths
(shove / dev_complete) would then commit that entire foreign tree onto the
pinned branch. That is precisely the main-hijack the pin exists to prevent, so a
half-enforcing pin is worse than none: it looks armed while the damage lands
anyway. This is the atomicity complement to
[[ax-sgit-pin-head-lock-scopes-enforcement]], which governs *which* transactions
the pin refuses at all.

### How to apply

- Emit both halves from `reference_transaction_script` in
  `crates/sgit-core/src/worktree_pin.rs`: the sentinel write at the refusal site,
  and the `aborted` branch that consumes it. Never ship one without the other.
- Bump `PIN_HOOKS_VERSION` whenever the script body changes so installed hooks
  are rewritten on the next pin/install.
- Restore with `git read-tree -m -u HEAD` only; it carries local modifications
  across. Never substitute `reset --hard` or `clean`.
- Cover a script change with a test that drives the REAL installed hook and
  asserts `git status --porcelain` is empty after a refused switch — asserting
  only on `HEAD` is exactly the check that passed while the pin was broken.

### Acceptance Checks

- `cargo test -p sgit-core worktree_pin -- --test-threads=1`
